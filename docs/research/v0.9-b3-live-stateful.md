# Ruhusa v0.9-B3 — Live-model stateful attack evaluation

**Status:** Unreleased experimental research code. Ruhusa v0.8.0 remains the published release.

B3 joins the B real-model proposal interface to B2's trusted stateful authorization
concepts. A real model proposes only `action`, `resource`, and `amount`; the
benchmark independently creates its own task, principal, grant, invocation,
revocation, and registered tool evidence. These security identities are **not**
accepted from model output. Protected tool execution remains **simulated**.

## Run

```bash
export RUHUSA_BENCHMARK_BASE_URL="https://api.openai.com/v1"
export RUHUSA_BENCHMARK_MODEL="gpt-4.1-mini"
export RUHUSA_BENCHMARK_API_KEY="$OPENAI_API_KEY"
uv run python -m research.live_stateful_benchmark \
  --trials 1 --output benchmark-results/v09b3-gpt41-mini.json
```

For Ollama, use `http://localhost:11434/v1`, `gemma3:270m` (a lightweight
smoke-test model), and an arbitrary key such as `ollama`. API requests may
incur provider charges. `RUHUSA_BENCHMARK_TIMEOUT` sets the HTTP timeout in
seconds; the default for B3 is 120.

Run network-free tests:

```bash
uv run pytest tests/test_v09_live_stateful_benchmark.py -v
uv run ruff format --check .
uv run ruff check .
uv run pytest
```

## Experimental protocol

Nine scenario prompts align with the B2 attack families. A scenario is
**exercised** only if the model proposes the target kind of action: the control
must generate a permitted operation; an attack must generate a disallowed one.
Otherwise the scenario is counted as unexercised, even if Ruhusa makes a
correct decision. Invalid JSON and `action=none` are not successful denials.

For each well-formed call, the benchmark creates an isolated, canonical in-memory
invocation and authorization environment. The trusted scenario determines task
mismatch, revocation, wrong tool, agent mismatch, expiry, and operation-reuse
context. The model cannot change those attributes. A separate, explicit oracle
calculates whether the proposal *should* be authorized, without inspecting the
Ruhusa decision. Both the permissive baseline and gated conditions receive the
same proposal; baseline execution means only a **simulated** side effect.

The report includes expected and actual outcomes, target coverage, false
denials, correct denials, and simulated unauthorized effects. Model responses
are not captured raw; only validated structured proposals are included in
reports. Do not use personal data in prompts. Avoid storing or publishing
private model inputs/outputs. API keys are not written to output.

## What this does not establish

- It does **not** prove identical-operation replay prevention or once-only side
  effects. `operation_reuse` attempts an **altered** operation under an already
  recorded invocation; an identical call is not considered an attack here.
- It does **not** test PostgreSQL durability, distributed concurrency, cryptographic
  workload identity, authenticated recovery evidence, or a production MCP adapter.
- One test run is descriptive, not statistical proof of an attack-resistance rate.
- Mocked tool executions do not prove production side-effect safety.
- The test fixtures are synthesized separately for each trial; a model cannot
  currently carry trusted state from one trial into another.

## Preliminary controlled GPT-4.1-mini result (10 trials per scenario)

A reported development run produced **90 valid model proposals** across nine
scenarios (one authorized control and eight unauthorized contexts). All ten
control proposals were allowed and all 80 unauthorized proposals were denied;
there were zero decision mismatches, zero false denials and zero unauthorized
**simulated** Ruhusa side effects. The permissive baseline simulated 80
unauthorized effects on the same proposals.

These counts describe the run, not an estimate of real-world attack-prevention
probability. Proposals were largely identical within each scenario, the trusted
security state was synthesized in-memory, and no real external side effects
occurred. Reproduce and archive the exact runner revision, model configuration,
scenario prompts, and generated JSON when preparing research results.
