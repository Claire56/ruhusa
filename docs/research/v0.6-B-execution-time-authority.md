# Ruhusa v0.6-B — Execution-Time Authority Validity

**Document status:** Active research note  
**Milestone:** v0.6-B  
**Package version:** remains 0.5.0 during active development  
**Verification status:** PENDING until the branch test suite is executed

---

## 1. Research Question

v0.6-A introduced one-claim-at-a-time execution state and demonstrated that:

```text
operation binding != execution uniqueness
```

That control still leaves a temporal problem. An invocation may be valid when
execution authority is claimed and invalid when the external side effect is
actually attempted.

v0.6-B asks:

> Is authorization at claim time sufficient when delegated authority, task
> validity, or policy state can change before a protected side effect occurs?

The working hypothesis is:

> **Authorization-time validity does not imply execution-time validity.**

---

## 2. Threat Model

The relevant workflow is:

```text
T0  human delegates authority
        |
T1  agent action is authorized
        |
T2  execution authority is claimed
        |
        |  authority may change here
        |  - grant revoked
        |  - task expires
        |  - policy changes
        v
T3  protected side effect executes
```

A v0.6-A `ExecutionPermit` proves that an invocation won its execution claim. It
does not prove that the underlying authorization conditions are still valid at
T3.

This creates an authorization-to-use time-of-check/time-of-use (TOCTOU) window.

---

## 3. Proposed Invariant

v0.6-B introduces the following candidate invariant:

> **EXE-02 — Live Authority at Execution Boundary:** A claimed invocation must
> still satisfy the complete Ruhusa authorization path immediately before a
> protected external side effect is attempted.

The revalidation evaluates current:

- task validity;
- delegation-chain validity;
- grant revocation state;
- canonical invocation provenance;
- canonical tool identity;
- effective scope;
- authorization policy.

The LLM does not perform or override this check.

---

## 4. New Control

`ExecutionController.revalidate_before_execution(request, permit)` re-runs
`Ruhusa.authorize()` at the execution boundary.

```text
LLM / agent proposes action
          |
          v
Ruhusa.authorize()
          |
          v
ExecutionStore.claim()
          |
          v
       CLAIMED
          |
          | time passes / workflow changes
          v
revalidate_before_execution()
          |
     +----+----+
     |         |
   ALLOW      DENY
     |         |
     |         v
     |      CANCELLED
     v
protected side effect
```

A denied revalidation moves the active execution attempt to `CANCELLED`.

`CANCELLED` is terminal. Ruhusa does not automatically resurrect the old
invocation if authority is later restored. A new trusted invocation should be
created.

---

## 5. Why Revalidation Uses the Full Authorization Path

v0.6-B does not add a second, reduced policy language for execution checks.

Instead, it reuses the same deterministic authorization path that established
the original decision. This matters because execution-time invalidity may arise
from several independent controls:

```text
task expires
grant revoked
delegation becomes temporally invalid
policy no longer matches
canonical invocation expires
trusted tool state fails
required security backend fails
```

A bespoke "revocation-only" check would leave the other transformations
unmediated.

## 7. Attack-First Interpretation

### Experiment 28 — Revocation Before Claim

This is a control experiment. `begin()` already re-runs `Ruhusa.authorize()`
before creating execution state. A grant revoked before `begin()` should not
create an execution claim.

### Experiment 29 — Revocation After Claim Without Revalidation

This intentionally reproduces the v0.6-A temporal gap:

```text
ALLOW
  |
claim
  |
revoke
  |
complete
```

`complete()` proves lifecycle ownership; it does not independently re-evaluate
authorization.

The expected baseline is therefore `GAP`.

### Experiment 30 — Revalidation After Post-Claim Revocation

The same attack is repeated through the new execution-time boundary:

```text
ALLOW
  |
claim
  |
revoke
  |
revalidate
  |
DENY -> CANCELLED
```

This is the direct before/after comparison for the v0.6-B control.

### Experiments 31–32 — Non-Revocation Authority Changes

The authorization context may become invalid without explicit grant
revocation. The task may expire or the policy store may cease to authorize the
operation.

These experiments test whether the control is truly "live authorization"
rather than merely a second revocation lookup.

### Experiment 33 — Permit Integrity

Successful re-authorization of the operation is insufficient if the caller
does not possess the currently active execution attempt. A stale or forged
`ExecutionPermit` must not pass the execution boundary.

### Experiment 34 — Fail-Closed Lifecycle State

If Ruhusa cannot determine whether the permit still owns the active claim, the
execution boundary must deny rather than assume the permit is valid.

### Experiment 35 — Residual TOCTOU Boundary

Execution-time revalidation narrows the temporal gap but does not eliminate it:

```text
revalidate -> ALLOW
        |
        | authority changes here
        v
external side effect
```

The authorization decision and a remote system's side effect are not one
atomic transaction.

This experiment is intentionally expected to remain a `GAP` in v0.6-B.

---

## 8. Security Claims Allowed After Successful Verification

If Experiments 28–34 pass as expected, v0.6-B may claim:

- claimed execution authority can be revalidated against live authorization
  state immediately before use;
- revocation that occurs before execution-time revalidation is observed;
- task expiry before revalidation is observed;
- current policy is re-evaluated before use;
- stale and forged execution permits do not satisfy the active-claim check;
- lifecycle-state failures during revalidation fail closed;
- denial at the execution boundary terminates the old invocation as
  `CANCELLED`.

It must **not** claim that revalidation is atomic with an external side effect.

---

## 9. Explicit Non-Claims

v0.6-B does not provide:

- distributed consensus across workers or pods;
- durable execution-state recovery;
- atomic revocation + external side effect;
- atomic authorization + external side effect;
- exactly-once external execution;
- downstream idempotency;
- reconciliation of `UNKNOWN` outcomes;
- policy-version or authority-epoch leases;
- prevention of authority changes after the final revalidation instant.

---

## 10. Dissertation Relevance

This phase models a property especially relevant to autonomous LLM-agent
systems. Agents may pause, replan, wait for tool availability, recover from
errors, or coordinate asynchronously after an initial authorization decision.

The resulting research distinction is:

```text
authority valid when planned
        !=
authority valid when executed
```

In the dissertation framing, this is one mechanism by which an AI-generated
workflow can experience **workflow authority drift**: the action reaching the
execution boundary no longer reflects the authority currently delegated by
the human principal.
