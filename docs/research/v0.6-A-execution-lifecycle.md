**Document status:** Validated research note

## Research boundary

v0.5 established trusted invocation provenance and operation binding, but it
intentionally retained exact same-operation invocation replay:

```text
operation binding != execution uniqueness
```

v0.6-A introduces a separate execution lifecycle instead of making
`Ruhusa.authorize()` consume invocation state.

## New components

- `ExecutionState`
- `ExecutionRecord`
- `ExecutionPermit`
- `ExecutionClaimResult`
- `ExecutionDecision`
- `InMemoryExecutionStore`
- `ExecutionController`

## State machine

```text
AVAILABLE --claim--> CLAIMED --complete--> COMPLETED
    ^                   |
    |                   +--uncertain--> UNKNOWN
    |
    +--release-before-execution-- CLAIMED
```

`UNKNOWN` deliberately has no automatic transition back to AVAILABLE.

## Experiments

- Exp 18: v0.5 exact replay baseline remains GAP through `authorize()`
- Exp 19: second execution claim BLOCKS
- Exp 20: concurrent claim race BLOCKS; exactly one winner
- Exp 21: completed invocation replay BLOCKS
- Exp 22: known pre-side-effect failure may safely retry (CONTROL)
- Exp 23: unknown external outcome retry BLOCKS
- Exp 24: stale/forged permit mutation BLOCKS
- Exp 25: expired execution authority BLOCKS
- Exp 26: authorization DENY does not consume execution state (CONTROL)
- Exp 27: execution-store failure fails closed

## Explicit non-claims

v0.6-A does not yet claim:

- distributed atomicity across processes or pods
- durable execution state
- atomic authorization + external side effect
- revocation re-check after claim
- task/policy change re-check after claim
- downstream idempotency
- exactly-once external side effects
- reconciliation of UNKNOWN outcomes

Those become v0.6-B / v0.6-C attack targets.
