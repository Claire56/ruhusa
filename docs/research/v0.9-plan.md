# v0.9 development plan — Agent Security Evaluation & Trusted Execution

**Status:** development; no v0.9 package published by this change.
**Base:** v0.8.0. Preserve the frozen v0.6 experiment artifact.

## Increment 1 — deterministic benchmark foundation (implemented)

`research/agent_attack_benchmark.py` evaluates a fixed set of proposed tool
calls under a permissive simulated control and the real Ruhusa `authorize()`
function. Run `PYTHONPATH=src python -m research.agent_attack_benchmark` to print JSON.

The labels *prompt injection*, *replanning*, and *substitution* describe the
hypothetical source of a proposed action. They are **not generated by an LLM**.
The replay does not establish real-agent attack resistance, MCP security,
execution-time guarantees, or statistical significance. It intentionally uses
weak self-asserted invocation provenance, never production identity assurance.
`baseline_executed` is a simulated permissive control, not a measured external
system. No real downstream side effects occur.

Metrics are raw counts with denominators and per-case records. Future model
experiments must record model/provider/version, prompts, seeds where supported,
policy version, authorized ground truth, repeats, tool side effects, and costs.
Never merge `GAP` experiments with `BLOCKS` outcomes as one success metric.

## Increment 2 — real model-driven agent benchmark (planned)

Add a reproducible agent runner and generated adversarial inputs; isolate
secrets and external tools in a sandbox. Include an independent side-effect
oracle and blinded ground-truth adjudication. Compare paired baseline and
Ruhusa runs under identical tasks. Collect variance across model runs and
report confidence intervals. Keep research dependencies outside `src/ruhusa`.

## Increment 3 — MCP integration (planned)

Implement an optional adapter with server-verified principal, immutable
canonical invocation, trusted tool identity, authorization-before-execution,
and explicit DENY / REQUIRE_APPROVAL responses. Verify both successful and
blocked tool calls and failure behavior with integration tests. Authorization
alone must not be represented as exactly-once execution.

## Increment 4 — trusted recovery evidence (planned)

Define verifier interfaces, authenticated evidence binding to execution claim
and attempt, replay rejection, audit persistence and fail-closed reconciliation.
No model-provided recovery claims may act as trusted evidence.

## Increment 5 — durable human approvals (proposed)

Bind approval to the exact principal, task, resource, action, canonical argument
digest and tool; verify approver identity, expiry, single-use semantics, and
revocation. Test across concurrent PostgreSQL-backed instances.

## Release gates

- Run the full CI suite, including PostgreSQL when available.
- No regression in existing fail-closed guarantees.
- Security claims supported by executable tests and documented limitations.
- Update README, CHANGELOG and release notes before packaging v0.9.0.
- Do not bump version until release scope and tests are complete.
