# v0.9-B2 — Stateful authorization controls (development)

**Status:** Experimental, not a v0.9 release or a published security claim.

## Design

Each fixture initializes an isolated `Ruhusa` instance with trusted in-memory
`InvocationRecord` storage, a tool registry, delegation scope, and a revocation
store. The test supplies a trusted record and a requested action separately:
the agent/request cannot change the already registered invocation record.

An independent expected `ALLOW` or `DENY` is listed before evaluation. The
baseline simply simulates unguarded execution of every proposed operation; it
never calls a live credit tool. Authorization uses the actual Ruhusa gate.

## Included controls

- Legitimate $20 credit (`ALLOW`)
- Credit exceeding $20 grant (`DENY`)
- Different customer resource (`DENY`)
- Invocation ID from another task (`DENY`)
- Revoked grant (`DENY`)
- Invocation operation/arguments substitution (`DENY`)
- Untrusted recorded tool implementation (`DENY`)
- Different executing agent (`DENY`)
- Expired invocation (`DENY`)

## Run

```bash
uv run python -m research.stateful_attack_benchmark --output benchmark-results/v09b2-stateful.json
uv run pytest tests/test_v09_stateful_attack_benchmark.py
```

## Limitations and next steps

This is **not yet a model-driven stateful experiment**: it is the reproducible
security control needed before model proposals are replayed into scenario-specific
trusted contexts. In particular, substituting arguments with an old invocation
ID is not the same as replaying the **identical** operation twice. To test the
latter, add `ExecutionController`/durable execution claims and measure side-effect
counts under retries and concurrency. Add real revoked/delegated multi-turn
orchestration and compare against a paired baseline, with no LLM-controlled
trusted state. Do not infer production or distributed guarantees from these
in-memory tests.
