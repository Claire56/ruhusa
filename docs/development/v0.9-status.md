# Ruhusa v0.9 development status

**Unreleased development.** The published stable distribution is **v0.8.0**
(schema v2). This repository snapshot contains v0.9 development implementations,
including **schema v3** in source; package metadata remains `0.8.0` and must not
be used to claim these changes are present in the published stable wheel.

## Milestones and evidence

| Workstream | Implementation in this snapshot | Remaining release gates |
| --- | --- | --- |
| A — Durable approvals | Operation-bound approval lifecycle and PostgreSQL schema v3 present | Authenticated approver integration, deployment validation, concurrency and upgrade CI |
| B — Real-model proposals | OpenAI-compatible model benchmark and offline tests present | Broader attack diversity and representative models |
| B2 — Stateful controls | Nine deterministic authorization fixtures present | Distributed/replay execution experiments |
| B3 — Live-model stateful evaluation | Real-model proposals paired with stateful Ruhusa checks; offline tests present | Multi-model/adaptive studies and reproducibility reporting |
| C — MCP | Transport-neutral guard, SDK handler, and optional real SDK round-trip test present | Authenticated HTTP transport, durable side-effect fencing and deployment tests |
| D1/D2 — Authenticated recovery | Signed evidence verification and opt-in PostgreSQL atomic receipt/state service present | Versioned migration, PostgreSQL CI, restricted legacy reconciliation APIs, trusted evidence source and key lifecycle |
| E — Release hardening | Not complete | Full integration CI, migration compatibility, threat model/API documentation and release artifacts |

**Observed development testing (not a release claim):** The B3 GPT-4.1-mini
experiment reported 90 valid proposals across nine scenarios and ten trials
per scenario: 80 expected denials, ten expected allows, and zero mismatches.
The experiments use trusted in-memory security fixtures and simulated side
effects; repeated prompts are not statistically independent, and these
results do not establish production security.

The optional MCP client/server in-process round trip was reported to pass
when MCP SDK v2 was supplied. The ordinary test suite skips it when the
optional dependency is absent. Neither result demonstrates authenticated
HTTP transport or exactly-once downstream effects.

## Critical trust boundaries

- `REQUIRE_APPROVAL` is not itself a verified human signature. Approver identity
  must be authenticated by trusted host infrastructure.
- Model-proposed tool arguments never establish trusted principal, task,
  delegation or tool identity. The MCP host supplies those bindings.
- D1 uses process-local replay tracking. D2 adds an opt-in PostgreSQL atomic
  receipt/state transaction, but **neither** restricts direct legacy reconciliation
  entry points or establishes trusted external provider outcome verification.
- Existing `UNKNOWN` execution recovery and cross-process execution fencing
  are separate mechanisms; a signed receipt alone does not make remote side
  effects atomic or exactly once.

## Version and upgrade policy

- Stable installation: `ruhusa==0.8.0` with PostgreSQL schema v2.
- Current development source: PostgreSQL schema v3 for approval records.
- Schema versions are independent of Python distribution versions.
- Do not publish a development wheel as the stable `0.8.0` artifact.
- Preserve v0.7→v0.8 migration coverage and separately test v0.7/v0.8→v0.9
  development upgrades.
