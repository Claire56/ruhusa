# Ruhusa 0.9.0 — Release notes

> **Pending PyPI publication.** The stable version on PyPI remains `0.8.0` until v0.9.0 is tagged and published. Install the wheel built from the release branch to evaluate before publication.

## Changes since 0.8.0

- Durable, operation-bound human approvals using PostgreSQL schema v3.
- Model-driven and stateful authorization attack benchmarks with controlled, simulated side effects.
- MCP tool authorization guard and SDK router, with optional real SDK protocol round-trip test.
- Signed authenticated recovery evidence and PostgreSQL reconciliation with receipt uniqueness and atomic state transitions.
- Schema v4 (`v3 → v4`) migration for durable recovery receipt storage.
- Default-deny direct legacy `reconcile_unknown()` access, unless an explicitly unsafe compatibility option is enabled.
- PostgreSQL distributed recovery tests covering process restart, concurrent reconciliation, failed transactions, and abrupt process termination before commit.

## Breaking changes and migration

**Direct legacy reconciliation is denied by default.** Replace callers of `reconcile_unknown()` with a trusted `PostgresAuthenticatedRecoveryService` integration. Avoid `allow_unsafe_legacy_reconciliation=True` in production. Host applications must authenticate the reconciler and restrict database roles.

**Schema upgrade:** published `0.8.0` uses schema v2; v0.9.0 uses schema v4 via `v2 → v3 → v4`. Back up the database first; test the upgrade against a copy; schema downgrade is not supported. See [migrations](../production/migrations.md).

## Installation (after publication)

```bash
pip install "ruhusa[postgres]==0.9.0"
```

This command is valid **after** v0.9.0 is published to PyPI. Until then, test using the wheel built from the release branch. Stable users should retain `ruhusa==0.8.0` until they have validated the upgrade path.

## Upgrade path from v0.8.0

1. Back up the PostgreSQL database.
2. Install the v0.9.0 wheel in a test environment.
3. Run `initialize_postgres_schema()` against a copy of the production database; confirm schema version reaches v4 and that `ruhusa_schema_migrations` contains rows `(1,2)`, `(2,3)`, `(3,4)`.
4. Confirm that `ruhusa_schema_migrations` history checksums match expectations and have not been modified.
5. Update application code: replace `reconcile_unknown()` calls with `PostgresAuthenticatedRecoveryService`.
6. Run the full PostgreSQL test suite with `RUHUSA_TEST_POSTGRES_DSN` set.
7. Validate in a staging environment before promoting to production.

## Security boundaries

Authorization decisions are deterministic, but do not replace trusted authentication of people, agents, transports, reconciler evidence issuers, or tool implementation registrations. Database privilege separation and signing-key rotation remain host responsibilities.

Neither MCP guards nor recovery receipts make external side effects atomic or exactly once. A signed receipt establishes that a trusted reconciler verified the outcome at a point in time; it does not make the external operation idempotent or guarantee network-partition behavior.

Benchmark outcomes are not general safety guarantees. The model-driven benchmarks used simulated side effects and a single model; results do not establish production security.

## Known limitations

- No atomic commit spanning external side effects and the Ruhusa database.
- Recovery evidence authenticity does not establish external outcome truth.
- Trusted host identity, signing key lifecycle, database privileges, and production transport authentication remain deployment responsibilities.
- D3c process/restart tests do not cover every failure injection scenario, network partitions, primary failover, or external exactly-once effects.

- Ruff check/format, full non-postgres test suite, and PostgreSQL-enabled integration suite via GitHub Actions.
- Real MCP SDK protocol round-trip executed and passed (not skipped) in release CI.
