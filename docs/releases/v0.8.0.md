# Ruhusa v0.8.0

Ruhusa v0.8.0 is the production-hardening release following the frozen v0.6
research artifact and the v0.7 production persistence release.

The authorization security model remains stable: default deny, fail closed,
least privilege, no delegated authority expansion, deterministic policy outside
the model, complete mediation, canonical invocation provenance, explicit
execution state, and mandatory audit for successful authorization.

## Highlights

### PostgreSQL schema migrations

PostgreSQL deployments now have an explicit schema version and transactional
migration path. v0.8 introduces schema version 2 and a migration-history table
with frozen migration checksums.

Initialization serializes schema changes with a PostgreSQL advisory transaction
lock, rejects future schemas, validates known migration history, and rolls back
failed migrations transactionally.

The supported upgrade path from the published `ruhusa==0.7.0` schema is tested
in release-candidate CI.

### Trusted integration boundary

`ruhusa.integrations.TrustedInvocationFactory` provides a framework-neutral
boundary for creating canonical invocation provenance from trusted runtime
observations.

Arguments and context are snapshotted before authorization inputs are exposed,
and trusted invocation/tool identity remains authoritative in the canonical
invocation record rather than being duplicated as self-asserted request fields.

### Optional FastAPI adapter

Install:

```bash
pip install "ruhusa[fastapi]"
```

The FastAPI adapter resolves identity from trusted server-side request state or
explicit trusted resolvers. It never falls back to client-controlled identity
headers.

The adapter prepares provenance only. It does not authenticate users, translate
authorization decisions into HTTP responses, or hide the explicit Ruhusa
execution lifecycle.

### Health and observability

v0.8 adds framework-neutral health probes and best-effort operational telemetry.

PostgreSQL health can check connectivity, schema compatibility, migration
history, and audit-chain integrity.

Operational telemetry remains separate from mandatory security audit. A
telemetry sink failure does not change an authorization or execution result;
audit persistence continues to preserve existing fail-closed behavior.

### Runtime lifecycle

`RuhusaRuntime` provides explicit ownership for application-managed resources,
including ordered startup, reverse-order shutdown, startup rollback,
health-gated startup, deterministic closed-resource behavior, and sanitized
lifecycle errors.

No resources are discovered or implicitly owned.

### Read-only diagnostic CLI

The installed `ruhusa` command includes:

```text
ruhusa version
ruhusa doctor
ruhusa postgres health
ruhusa postgres schema
ruhusa postgres audit
```

PostgreSQL diagnostics are read-only. The CLI does not initialize schemas,
migrate databases, create or revoke grants, reconcile UNKNOWN executions, or
perform protected side effects.

Raw PostgreSQL DSNs are read from environment variables rather than accepted as
command-line values.

## PostgreSQL schema

v0.8 uses PostgreSQL schema version 2.

The supported path is:

```text
ruhusa 0.7.0 schema v1
        ↓
transactional migration
        ↓
ruhusa 0.8.0 schema v2
```

Downgrades remain unsupported.

## Compatibility

Python 3.12 or newer is required.

Base install:

```bash
pip install ruhusa==0.8.0
```

PostgreSQL:

```bash
pip install "ruhusa[postgres]==0.8.0"
```

FastAPI:

```bash
pip install "ruhusa[fastapi]==0.8.0"
```

Both optional integrations:

```bash
pip install "ruhusa[postgres,fastapi]==0.8.0"
```

PostgreSQL and FastAPI remain optional and are not imported by the base root
package.

## Security boundaries that remain unchanged

v0.8 does not claim exactly-once behavior for arbitrary downstream side
effects.

UNKNOWN execution outcomes still require trusted reconciliation.

The PostgreSQL audit chain is tamper-evident but is not an immutable ledger
against a privileged database administrator.

Ruhusa does not provide cryptographic agent identity.

## Release validation

The release candidate must pass:

- the complete unit/integration test suite;
- PostgreSQL integration tests;
- clean base-wheel installation with no optional dependencies;
- wheel installation with PostgreSQL and FastAPI extras;
- installed CLI smoke tests;
- a real published v0.7.0 PostgreSQL schema upgraded by the v0.8.0 wheel;
- the external FastAPI smoke application regression suite.
